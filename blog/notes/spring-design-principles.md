스프링을 처음 배우면 `@Bean`, `@Configuration`, DI 컨테이너 같은 낯선 기능부터 만나게 된다. 그래서 스프링을 **외울 게 많은 프레임워크**로 느끼기 쉽다. 하지만 이 기능들은 모두 하나의 질문에 대한 답이다.

> 구현이 바뀌어도 코드를 고치지 않으려면 어떻게 해야 할까?

답은 아래 네 가지 설계 원칙에 있다.

---

## 1. 역할과 구현을 나눈다

요구사항은 바뀐다. 그래서 바뀔 수 있는 것은 인터페이스(역할)로 정의하고, 구현 클래스는 갈아끼울 수 있게 둔다. 구현이 바뀌어도 역할 사이의 협력 관계는 그대로 재사용된다.

스프링에서는 컨테이너가 구현 객체를 등록, 관리 및 갈아끼워 준다.

## 2. 책임을 나눠 맡긴다

역할을 나눴다면, 각 객체가 맡을 일도 나눠야 한다. 객체는 자기 책임만 수행하고 나머지는 다른 역할에 위임한다. 위임받는 쪽이 바뀌어도 위임하는 쪽은 바뀌지 않는다.

스프링에서 가장 큰 위임은 **객체를 생성하고 연결하는 일**이다.  
이 일을 스프링 컨테이너에 맡기고, 클라이언트는 로직 실행만 담당한다.

## 3. DIP: 추상화에만 의존한다

이렇게 나눈 구조가 제대로인지는 의존 방향으로 확인한다. DIP는 추상화에 의존하고, 구체 클래스에 의존하지 말라는 원칙이다.

흔한 위반은 클라이언트가 구현 클래스를 직접 `new` 하는 코드다.

```java
class Client {
    // 나쁜 예: Repo(추상)와 MemoryRepo(구체) 둘 다에 의존한다
    private final Repo repo = new MemoryRepo();
}
```

스프링은 DI(의존관계 주입)로 구현 객체를 밖에서 넣어 준다. 클라이언트는 생성자로 받기만 하면 된다.

```java
class Client {
    // 좋은 예: Repo(인터페이스)에만 의존하고, 구현 객체는 밖에서 받는다
    private final Repo repo;
    Client(Repo repo) { this.repo = repo; }
}
```

## 4. OCP: 확장에는 열리고, 변경에는 닫힌다

의존 방향이 맞으면 변경에도 강해진다. OCP는 기능을 바꾸거나 늘려도 기존 코드를 고치지 않아야 한다는 원칙이다. 구현 클래스를 바꿀 때 클라이언트 코드를 고쳐야 한다면 OCP를 어긴 것이다.

스프링에서는 구현 클래스 선택을 설정 정보가 맡아, 구현을 바꿔도 클라이언트 코드는 그대로 둘 수 있다.

---

| 원칙 | 한 줄 요약 | 스프링이 돕는 방식 |
| --- | --- | --- |
| 역할과 구현 분리 | 바뀔 수 있는 건 인터페이스로 | 컨테이너가 구현 객체를 관리하고 교체 |
| 책임의 위임 | 자기 일만, 나머지는 위임 | 생성과 연결은 컨테이너에 |
| DIP | 추상화에만 의존 | DI로 구현 객체 주입 |
| OCP | 확장은 열고, 변경은 닫고 | 설정만 바꿔 교체 |

결국 스프링은 이 원칙들을 지키기 위한 도구다. 기능을 외우기 전에 왜 이런 구조가 필요한지부터 이해하면, 스프링 코드가 훨씬 자연스럽게 읽힌다.

AOP(Aspect-Oriented Programming, 관점 지향 프로그래밍)는 여러 곳에 공통으로 들어가는 부가 기능을 핵심 로직에서 떼어 내 한곳에 모아 관리하는 프로그래밍 방법이다.

객체 지향은 프로그램을 클래스 단위로 잘 나누지만, 로깅이나 실행 시간 측정처럼 여러 클래스에 똑같이 필요한 기능은 어느 한 클래스에 담기 어렵다. AOP는 이런 기능을 **애스펙트**(Aspect)라는 별도 모듈로 묶어 객체 지향을 보완한다.

이름도 여기서 나왔다. Aspect는 대상의 한 '면'이라는 뜻으로, 기능이라는 면 말고 로깅 같은 다른 면을 단위로 프로그램을 짠다는 의미에서 '관점 지향'이라고 부른다.

AOP 개념은 1990년대 후반 제록스 PARC 연구소의 그레고르 킥제일스(Gregor Kiczales) 연구팀이 정립했고, 이 팀이 만든 자바용 구현체가 AspectJ다.

## 횡단 관심사

여러 클래스를 가로질러 반복되는 관심사를 **횡단 관심사**(cross-cutting concern)라고 한다. AOP는 이를 핵심 로직에서 분리하는 데 사용한다.

| 구분 | 뜻 | 예 |
| --- | --- | --- |
| 핵심 관심사 | 해당 기능이 본래 하려는 일 | 회원 조회, 주문 처리 |
| 부가 관심사 | 핵심 로직 외에 여러 곳에서 필요한 일 | 로깅, 실행 시간 측정, 캐싱 |

부가 기능을 각 메서드에 직접 넣으면 세 가지 문제가 생긴다.

- 같은 코드가 수십, 수백 군데에 반복된다.
- 로깅 방식 하나를 바꾸려 해도 여러 곳을 고쳐야 한다.
- 비즈니스 로직보다 부가 코드가 많아져 읽기 어렵다.

예를 들어 실행 시간을 측정하려면 시작 시간을 기록하고, 메서드가 끝나면 걸린 시간을 출력해야 한다. 대상 메서드가 수십 개라면 같은 틀이 수십 번 반복된다.

### 대표적인 쓰임

AOP는 여러 메서드에 같은 틀로 반복되는 일, 특히 실행 전후나 예외 시점에 붙는 일에 사용한다.

| 쓰임 | 부가 기능이 하는 일 |
| --- | --- |
| 로깅 | 호출된 메서드, 인자, 반환값 등을 기록한다 |
| 실행 시간 측정 | 실행 전후 시간을 재서 느린 메서드를 찾는다 |
| 캐싱 | 조건에 맞는 저장 결과가 있으면 원래 메서드 대신 반환한다 |

## 핵심 용어

**무엇을 실행할지**를 뜻하는 어드바이스와 **어디에 적용할지**를 고르는 포인트컷을 묶은 것이 애스펙트다.

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| 애스펙트(Aspect) | 부가 기능과 적용 위치를 모듈화한 것 | 로깅 애스펙트 |
| 어드바이스(Advice) | 적용 지점에서 실행할 코드 | 실행 시간을 재고 출력하는 코드 |
| 조인 포인트(Join Point) | AOP 구현체가 지원하는 적용 가능 지점 | 메서드 실행, 메서드 호출, 필드 접근, 객체 생성 등 |
| 포인트컷(Pointcut) | 조인 포인트 중 적용할 곳을 고르는 조건 | 특정 타입의 메서드, 특정 애노테이션이 붙은 메서드 |
| 타깃(Target) | 부가 기능을 적용받는 대상 객체 | 실행 시간을 측정할 서비스 객체 |
| 위빙(Weaving) | 애스펙트를 대상 코드와 결합하는 과정 | 바이트코드 변환 등 |

지원하는 조인 포인트는 구현마다 다르다. AspectJ는 메서드 실행뿐 아니라 필드 접근 등도 지원하지만, 스프링의 프록시 기반 AOP는 프록시를 통한 메서드 호출을 대상으로 한다. 프록시를 이용한 결합은 런타임 위빙이라고 설명하기도 하지만, AspectJ의 바이트코드 위빙과는 구분해야 한다.

## 예제: 실행 시간 측정

서비스 메서드의 실행 시간을 측정하려면 각 메서드에 코드를 넣는 대신 애스펙트 하나를 작성할 수 있다. 다음은 AspectJ의 애노테이션 스타일인 `@AspectJ` 문법을 사용한 예제다.

```java
@Aspect
public class TimeTraceAspect {

    @Around("execution(* *..*Service.*(..))")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            long elapsed = System.nanoTime() - start;
            System.out.println(joinPoint.getSignature()
                    + " 실행 시간: " + elapsed / 1_000_000.0 + "ms");
        }
    }
}
```

- `@Aspect`는 애스펙트임을 표시한다.
- `@Around`의 표현식은 이름이 `Service`로 끝나는 타입의 메서드 실행을 선택한다. 실제 적용 범위는 사용하는 AOP 구현과 프록시 제약에 따라 달라진다.
- `trace()` 본문이 어드바이스다. `proceed()`로 다음 어드바이스 또는 타깃 실행을 진행한다.
- 경과 시간 측정에는 시스템 시각 변경의 영향을 받는 `currentTimeMillis()`보다 `nanoTime()`이 적합하다.

> **애노테이션만으로 실행되지는 않는다**: AspectJ로 실행하려면 컴파일 또는 로드 시 위빙 구성이 필요하다. 스프링 AOP에서도 이 문법을 사용할 수 있지만, 애스펙트를 스프링 빈으로 등록하고 AOP가 활성화되어 있어야 한다. AspectJ 문법을 쓴다고 곧 AspectJ 위빙을 사용하는 것은 아니다.

### 어드바이스의 종류

| 어드바이스 | 실행 시점 |
| --- | --- |
| Before | 대상 실행 전 |
| After Returning | 정상 반환 후 |
| After Throwing | 예외가 전파될 때 |
| After | 정상 반환과 예외 여부에 관계없이 종료 후 |
| Around | 실행 전후를 감싸며 실행 여부, 반환값, 예외를 제어한다 |

필요한 시점만 다루는 어드바이스를 선택하면 의도가 더 명확하다. Around는 강력하지만 `proceed()` 호출 누락이나 잘못된 예외 처리로 동작을 바꿀 수도 있다.

## AOP는 어떻게 실현되나

프록시 방식부터 보면 AOP의 동작을 이해하기 쉽다. 원본 객체는 그대로 두고, 앞에서 호출을 받아 부가 기능을 수행하는 객체를 하나 둔다.

### 손으로 감싸 보기

다음은 서비스 인터페이스와 구현체가 준비되어 있다고 가정한 코드다.

```java
class MemberServiceTimer implements MemberService {
    private final MemberService target;

    public MemberServiceTimer(MemberService target) {
        this.target = target;
    }

    @Override
    public Member findMember(long id) {
        long start = System.nanoTime();
        try {
            return target.findMember(id);
        } finally {
            double elapsedMs = (System.nanoTime() - start) / 1_000_000.0;
            System.out.println("실행 시간: " + elapsedMs + "ms");
        }
    }
}
```

호출하는 쪽에 원본 대신 이 객체를 넘기면, 원본 코드를 바꾸지 않고 실행 시간을 측정할 수 있다. 수동으로 적용한 프록시 또는 데코레이터 형태의 구조다.

문제는 양이다. 메서드가 1000개라면 위임 메서드를 반복해서 작성해야 한다. 측정 코드를 공통 도구로 빼더라도 어디서 호출할지 연결하는 작업은 남는다.

### 도구가 결합을 맡는다

AOP 도구를 사용하면 개발자는 어드바이스와 포인트컷을 정의하고, 대상에 결합하는 작업은 도구에 맡길 수 있다.

개념적으로는 다음 흐름이다.

1. 적용 가능한 대상과 지점을 확인한다.
2. 포인트컷 조건에 맞는지 판단한다.
3. 해당 실행에 어드바이스가 참여하도록 연결한다.

구현체가 모든 메서드에 감싸는 코드를 개별 생성한다는 뜻은 아니다. 프록시의 호출 처리 체인을 사용하거나 실제 바이트코드를 변환하는 등 구현 방식은 다르다.

**애노테이션은 표시일 뿐이다.** 포인트컷에서 애노테이션을 조건으로 쓸 수 있지만, 애노테이션 자체가 부가 기능을 실행하는 것은 아니다. 택배 상자의 ‘취급 주의’ 스티커처럼, 표시를 읽고 행동하는 주체가 따로 필요하다. 메서드 이름이나 타입 같은 조건으로도 적용 대상을 고를 수 있다.

**설계는 개발자, 결합은 도구의 역할이다.** 무엇을 어디에 적용할지 정하는 책임은 개발자에게 있다. 프레임워크가 객체를 만들고 전달하는 흐름을 관리하면, 그 과정에서 프록시를 원본 대신 전달하기도 쉽다. 스프링이 제공하는 트랜잭션처럼 이미 준비된 부가 기능은 개발자가 애노테이션과 설정으로 사용하는 경우가 많다.

## 위빙과 프록시 방식

AspectJ의 위빙과 스프링 AOP의 프록시 방식은 다음처럼 구분할 수 있다.

| 방식 | 결합 방법 | 특징 |
| --- | --- | --- |
| 컴파일 시 위빙 | 컴파일 과정에서 애스펙트를 결합한다 | AspectJ 컴파일러 등 별도 구성이 필요하다 |
| 컴파일 후 위빙 | 이미 컴파일된 클래스 파일을 변환한다 | 기존 바이트코드에도 적용할 수 있다 |
| 로드 시 위빙 | JVM이 클래스를 로딩할 때 바이트코드를 변환한다 | 에이전트나 클래스 로더 등의 구성이 필요하다 |
| 런타임 프록시 | 원본 앞에서 호출을 받는 프록시 객체를 사용한다 | 바이트코드 위빙 없이 프록시를 통과하는 메서드 실행에 적용한다 |

로드 시 위빙도 애플리케이션 실행 과정에서 일어날 수 있다. 따라서 단순히 ‘실행 전은 위빙, 실행 중은 프록시’로 나누면 정확하지 않다.

### 프록시의 호출 흐름

프록시는 원본 객체 앞에서 호출을 대신 받는 대리 객체다. 클라이언트는 프록시를 호출하고, 프록시는 필요한 부가 기능을 실행하면서 타깃에 위임한다.

```mermaid
flowchart LR
    C["<b>클라이언트</b>"] -->|"호출"| P["<b>프록시</b><br/>부가 기능 실행<br/>타깃 호출 조율"]
    P -->|"위임"| T["<b>타깃</b><br/>핵심 로직"]
    T -.->|"반환 또는 예외"| P
    P -.->|"결과 전달"| C
```

### 프록시 방식의 한계

프록시 기반 AOP는 호출이 프록시를 통과해야 동작한다.

- **내부 호출**: 타깃 내부에서 `this.otherMethod()`를 호출하면 프록시를 다시 거치지 않는다. 해당 메서드의 어드바이스도 새로 적용되지 않는다. 역할에 맞게 별도 객체로 분리하는 것이 흔한 해결책이다.
- **적용 지점**: 필드 접근이나 생성자 실행 자체는 프록시 기반 AOP의 적용 대상이 아니다.
- **직접 생성한 객체**: 원본을 `new`로 만들고 프록시 없이 사용하면 부가 기능이 적용되지 않는다.
- **프록시 유형별 제약**: 인터페이스 기반인지 클래스 상속 기반인지에 따라 적용 가능한 메서드가 다르다. 예를 들어 상속 기반 프록시는 `final` 메서드를 재정의해 가로챌 수 없다.

AspectJ 위빙은 자기 호출이나 필드 접근처럼 프록시로 다루기 어려운 지점도 지원한다. 다만 위빙 구성과 지원하는 조인 포인트를 확인해야 하므로 제약이 전혀 없는 것은 아니다.

## 다른 언어의 유사한 기법

횡단 관심사를 분리하려는 생각은 자바에만 한정되지 않는다. 다른 언어와 프레임워크에서도 비슷한 목적의 도구를 찾을 수 있다.

| 언어 | 활용할 수 있는 수단 | 예 |
| --- | --- | --- |
| 자바 | AspectJ, 동적 프록시 | 스프링 AOP의 트랜잭션과 보안 처리 |
| 파이썬 | 데코레이터, 래퍼 | 함수 실행 전후 로깅, 웹 미들웨어 |
| 자바스크립트 | 함수 래퍼, `Proxy` | 호출 가로채기, Express 미들웨어 |
| TypeScript | 데코레이터와 메타데이터, 인터셉터 | NestJS 인터셉터 등 |

이 도구들이 모두 같은 AOP 모델을 제공하는 것은 아니다. 데코레이터는 감쌀 대상을 지정하는 수단이고, 미들웨어는 주로 요청 처리 파이프라인에 참여한다. 자바스크립트 `Proxy`도 바이트코드를 위빙하는 기능이 아니라 객체 연산을 가로채는 언어 기능이다.

## AOP와 객체 지향

AOP는 관심사 분리를 돕는 대신 실행 흐름의 명시성을 일부 낮춘다. 객체 지향을 보완하는 장점과 함께 주의할 점도 있다.

| 관점 | 얻는 것 | 주의할 점 |
| --- | --- | --- |
| 책임 분리 | 핵심 로직과 부가 기능을 분리한다 | 클래스 외부에서 실행 동작이 달라진다 |
| 가독성 | 클래스에 핵심 로직이 잘 드러난다 | 클래스만 읽으면 적용된 부가 기능이 보이지 않을 수 있다 |
| 유지보수 | 공통 기능의 수정 지점을 줄인다 | 리팩터링으로 포인트컷 적용 범위가 바뀔 수 있다 |
| 디버깅 | 반복 래퍼 코드를 직접 관리하지 않아도 된다 | 프록시와 어드바이스의 호출 흐름까지 확인해야 한다 |

특히 다음 두 가지 문제를 기억하면 좋다.

- **멀리서 일어나는 작용(action at a distance)**: 코드의 동작이 그 코드와 떨어진 설정이나 애스펙트에서 결정된다.
- **깨지기 쉬운 포인트컷 문제(fragile pointcut problem)**: 이름이나 구조를 바꿨을 때 컴파일 오류 없이 적용 범위가 달라질 수 있다.

이를 줄이려면 세 가지 기준을 생각해 볼 수 있다.

1. 정말로 여러 곳에 공통으로 필요한 기능에 사용한다.
2. 핵심 비즈니스 규칙을 애스펙트 안에 숨기지 않는다.
3. 적용 범위를 명확히 하고 테스트로 확인한다. 애노테이션을 활용하면 의도를 코드에 드러내고 이름 변경에 대한 의존을 줄일 수 있지만, 표시 누락이나 잘못된 조건까지 막아 주지는 않는다.

---

AOP는 여러 곳에 반복되는 기능을 모듈로 분리하고, 적용 대상과 연결하는 일을 도구에 맡기는 방법이다. 핵심은 애노테이션 자체가 아니라 **부가 기능과 적용 규칙을 분리하는 것**이다.

프록시로 구현한다면 호출이 프록시를 통과하는지도 함께 봐야 한다. 무엇이 적용되는지뿐 아니라 어디에서 적용되지 않는지까지 이해해야, 핵심 로직을 간결하게 유지하면서도 실행 흐름을 놓치지 않을 수 있다.

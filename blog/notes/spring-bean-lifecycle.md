DB 커넥션 풀이나 네트워크 소켓처럼, 애플리케이션이 시작할 때 미리 연결해 두고 끝날 때 연결을 닫아야 하는 객체가 있다. 이런 객체에는 초기화와 종료 작업이 필요하다.

그런데 생성자에서 초기화를 시작하면, 필요한 의존관계가 아직 주입되지 않았을 수 있다. 그렇다면 초기화는 언제, 어디서 해야 할까?

---

## 생성자에서 초기화하면 생기는 일

생성자는 객체를 만들 때 가장 먼저 실행된다. 그런데 수정자 주입처럼 객체를 만든 **다음에** 들어오는 의존관계는, 생성자가 실행되는 시점에는 아직 비어 있다. 그래서 생성자에서 주입받을 값을 쓰는 초기화 작업을 하면, `null`을 가지고 일하게 된다.

```java
public class Client {
    private Repo repo;

    public Client() {
        repo.connect();  // 아직 주입 전이라 repo는 null
    }

    @Autowired
    public void setRepo(Repo repo) {  // 객체가 만들어진 뒤에 호출된다
        this.repo = repo;
    }
}
```

## 스프링 빈의 생명주기

수정자 주입이나 필드 주입에서는 객체를 먼저 만들고, 그다음에 의존관계를 주입한다. 생성자 주입은 객체를 생성할 때 의존관계도 함께 전달한다. 어느 방식이든 스프링은 의존관계 주입을 마친 뒤 초기화 콜백을 호출하므로, 이 시점에 외부 연결 같은 준비 작업을 시작할 수 있다.

문제는 그 시점을 개발자가 알기 어렵다는 것이다. 그래서 스프링은 **콜백**으로 알려 준다. 주입이 끝나면 초기화 콜백을, 컨테이너가 종료되기 직전에는 소멸 전 콜백을 호출해 준다.

```mermaid

    accDescr: 컨테이너가 빈을 생성하고 의존관계를 주입한 뒤 초기화 콜백을 호출한다. 빈을 사용한 다음 정상 종료 과정에서 소멸 전 콜백으로 자원을 정리한다. 생성자 주입은 빈 생성과 함께 이뤄진다.
    A["컨테이너 생성"] --> B["빈 생성"] --> C["의존관계 주입"] --> D["<b>초기화 콜백</b>"] --> E["사용"] --> F["<b>소멸 전 콜백</b>"] --> G["컨테이너 종료"]
    style D stroke-width:2px
    style F stroke-width:2px
```

- **초기화 콜백**: 빈이 생성되고 의존관계 주입이 끝난 뒤 호출된다.
- **소멸 전 콜백**: 컨테이너가 관리하는 빈의 종료 단계에서 호출된다. 메모리를 해제하는 시점이 아니라, 연결 해제 등 자원을 정리하는 시점이다.

> **객체 생성과 초기화는 분리한다**: 생성자는 필수 값을 받아 객체를 만드는 데 집중하고, 외부 연결처럼 무거운 작업은 초기화 단계로 나누는 것이 유지보수에 좋다. 내부 값을 조금 바꾸는 정도의 가벼운 초기화라면 생성자에서 처리해도 된다.

> **참고**: 싱글톤 빈은 보통 컨테이너 초기화 과정에서 생성되지만, 지연 초기화된 빈은 처음 필요할 때 생성된다. 컨테이너가 정상적으로 닫히면 소멸 전 콜백이 호출된다. 요청 스코프 등은 해당 스코프의 종료 시점에 정리되지만, 프로토타입 빈은 생성과 초기화 이후 컨테이너가 소멸 콜백을 자동으로 호출하지 않으므로 사용하는 쪽에서 정리해야 한다.

## 콜백을 거는 세 가지 방법

스프링은 생명주기 콜백을 세 가지 방법으로 지원한다.

### 1. InitializingBean, DisposableBean 인터페이스

두 인터페이스를 구현하면, 스프링이 각 인터페이스에 정해진 메서드를 호출해 준다.

- `InitializingBean`의 `afterPropertiesSet()`: 의존관계 주입이 끝나면 호출된다. 초기화를 맡는다.
- `DisposableBean`의 `destroy()`: 컨테이너가 종료되기 직전에 호출된다. 소멸을 맡는다.

```java
public class Client implements InitializingBean, DisposableBean {

    @Override  // InitializingBean: 의존관계 주입이 끝나면 호출
    public void afterPropertiesSet() { /* 외부 연결 등 초기화 작업 */ }

    @Override  // DisposableBean: 컨테이너 종료 직전에 호출
    public void destroy() { /* 연결 해제 등 종료 작업 */ }
}
```

초기화 콜백은 의존관계 주입이 끝난 뒤에 호출되므로, 주입받은 값을 안심하고 쓸 수 있다. 소멸 전 콜백은 컨테이너가 종료되기 직전에 호출된다.

하지만 이 방식은 단점이 분명하다.

- 스프링 전용 인터페이스라 코드가 스프링에 의존한다.
- 초기화와 소멸 메서드의 이름을 바꿀 수 없다.
- 코드를 고칠 수 없는 외부 라이브러리에는 적용할 수 없다.

> **참고**: 스프링 초창기에 나온 방법으로, 지금은 더 나은 방법이 있어 거의 쓰지 않는다.

### 2. @Bean의 initMethod, destroyMethod

설정 정보에 초기화와 소멸 메서드의 이름을 적는다.

```java
public class Client {
    public void init()  { /* 외부 연결 등 초기화 작업 */ }
    public void close() { /* 연결 해제 등 종료 작업 */ }
}

@Bean(initMethod = "init", destroyMethod = "close")
public Client client() { return new Client(); }
```

- 메서드 이름을 자유롭게 정할 수 있다.
- 빈이 스프링 코드에 의존하지 않는다.
- 코드가 아니라 설정 정보에 적기 때문에, 코드를 고칠 수 없는 외부 라이브러리에도 쓸 수 있다.

> **종료 메서드 추론**: `destroyMethod`의 기본값은 `(inferred)`다. 라이브러리는 대부분 종료 메서드 이름으로 `close`나 `shutdown`을 쓰는데, 스프링이 이 이름의 메서드를 찾아 자동으로 호출해 준다. 그래서 `@Bean`으로 등록하면 종료 메서드를 따로 적지 않아도 잘 동작한다. 추론을 끄려면 `destroyMethod = ""`로 지정한다.

### 3. @PostConstruct, @PreDestroy

메서드에 애노테이션만 붙이면 된다.

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;

public class Client {

    @PostConstruct
    public void init()  { /* 외부 연결 등 초기화 작업 */ }

    @PreDestroy
    public void close() { /* 연결 해제 등 종료 작업 */ }
}
```

- 애노테이션 하나만 붙이면 되니 가장 편리하다.
- 스프링 전용이 아니라 JSR-250에서 출발한 Jakarta Annotations 표준이므로, 이를 지원하는 다른 컨테이너에서도 사용할 수 있다.
- 컴포넌트 스캔과 잘 어울린다.
- 다만 코드를 고칠 수 없는 외부 라이브러리에는 붙일 수 없다.

> **패키지**: 예전에는 `javax.annotation` 패키지였고, 스프링 부트 3(스프링 6)부터는 `jakarta.annotation` 패키지를 쓴다.

### 세 가지 방법 비교

| 방법 | 스프링 의존 | 메서드 이름 | 외부 라이브러리 |
| --- | --- | --- | --- |
| 인터페이스 | 있음 | 고정 | 적용 불가 |
| `@Bean` 속성 | 없음 | 자유 | 적용 가능 |
| `@PostConstruct`, `@PreDestroy` | 없음 | 자유 | 적용 불가 |

직접 작성한 클래스라면 애노테이션으로 생명주기를 드러내고, 외부 라이브러리라면 설정 클래스에서 메서드를 지정하면 된다. 선택 기준은 콜백을 넣을 코드를 직접 수정할 수 있느냐다.

---

수정자 주입이나 필드 주입에서는 생성자가 실행될 때 의존관계가 아직 채워지지 않는다. 생성자 주입이라면 의존 객체를 받을 수 있지만, 외부 연결처럼 별도로 관리할 준비 작업은 초기화 콜백으로 분리하는 편이 좋다. 스프링은 의존관계 주입을 마친 시점과 자원을 정리해야 할 시점을 콜백으로 알려 준다.

방법은 세 가지지만 고민할 것은 많지 않다. 평소에는 `@PostConstruct`와 `@PreDestroy`를 쓰고, 코드를 고칠 수 없는 외부 라이브러리만 `@Bean`의 `initMethod`와 `destroyMethod`로 처리하면 된다.

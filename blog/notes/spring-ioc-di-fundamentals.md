인터페이스를 쓰는 이유는 구현 클래스를 바꿔도 클라이언트 코드를 그대로 두기 위해서다.

그런데 클라이언트가 구현 클래스를 직접 `new` 하면 결국 그 구현 클래스에 묶인다.
그렇다고 `new`를 지우면 넣어 줄 객체가 없어 NullPointerException가 난다.

그 빈자리를 바깥에서 채워 주는 방법이 **DI**(의존관계 주입)이다.

---

## 관심사의 분리: 생성과 실행을 나눈다

구현 클래스를 직접 생성하는 클라이언트는 두 가지 일을 함께 수행한다.

- **생성과 연결**: 필요한 구현 객체를 만들고 연결한다.
- **실행**: 연결된 객체를 사용해 비즈니스 로직을 실행한다.

이 두 책임을 나누는 것이 **관심사의 분리**다.

공연에 비유하면 배우는 배역을 수행하는 데 집중하고, 배우를 섭외하는 일은 공연 기획자가 맡는 것과 같다. 객체도 실행에만 집중하고 생성과 연결은 외부에 맡기면 하나의 책임만 갖게 되므로 SRP(단일 책임 원칙)를 지키기 쉬워진다.

---

## 객체의 생성과 연결을 설정 클래스로 옮긴다

먼저 객체를 생성하고 연결하는 책임을 별도의 설정 클래스로 옮길 수 있다.

```java
// 클라이언트는 사용할 객체를 생성자로 받는다.
class Client {
    private final Repo repo;
    Client(Repo repo) { this.repo = repo; }
}

// 설정 클래스가 객체의 생성과 연결을 담당한다.
class AppConfig {
    Client client() { return new Client(new MemoryRepo()); }
}
```

이제 `Client`는 `Repo` 인터페이스에만 의존한다. 어떤 구현 객체를 사용할지는 `AppConfig`가 결정한다.

다만 아직은 `AppConfig`를 호출해 객체를 만들고, 만들어진 객체를 관리하는 일까지 개발자의 몫이다.

스프링을 사용하면 이 역할을 컨테이너에 맡길 수 있다. 설정 클래스에 `@Configuration`과 `@Bean`을 붙이면, 스프링 컨테이너가 설정 정보를 읽어 객체를 생성하고 의존관계를 연결한 뒤 관리한다.

```java
@Configuration
public class AppConfig {
    @Bean
    public Repo repo() { return new MemoryRepo(); }

    @Bean
    public Client client() { return new Client(repo()); }
}
```

```java
ApplicationContext ac =
    new AnnotationConfigApplicationContext(AppConfig.class);

Client client = ac.getBean("client", Client.class);
```

각 요소의 역할은 다음과 같다.

- `@Configuration`: 해당 클래스가 스프링 설정 클래스임을 나타낸다.
- `@Bean`: 메서드가 반환한 객체를 스프링 빈으로 등록한다. 기본 빈 이름은 메서드 이름이다.
- `ApplicationContext`: 스프링 컨테이너다. 등록된 빈을 조회하고 관리한다.

구현을 교체할 때는 클라이언트가 아니라 설정 정보만 변경하면 된다.

```java
@Bean
public Repo repo() {
    return new DbRepo(); // MemoryRepo에서 DbRepo로 교체
}
```

### 스프링 빈이란?

**스프링 빈**은 스프링 컨테이너에 등록되어 관리되는 객체다. 평범한 자바 객체와 다를 게 없고, 누가 만들고 연결하느냐만 다르다. 직접 `new`로 만든 객체는 개발자가 생성과 연결을 책임지고, 스프링 빈은 컨테이너가 책임진다.

## IoC: 객체에 대한 제어권을 외부로 넘긴다

객체를 직접 생성할 때는 클라이언트가 필요한 구현 객체를 선택하고 생성한다. 반면 컨테이너를 사용하면 어떤 객체를 생성하고 연결할지 컨테이너가 결정하며, 클라이언트는 자신의 로직만 실행한다.

이처럼 객체 생성과 호출에 대한 제어권이 외부로 넘어가는 것을 **IoC(제어의 역전)** 라고 한다.

> 내 코드가 전체 흐름을 제어하면서 필요한 기능을 호출하면 라이브러리이고, 프레임워크가 전체 흐름을 제어하면서 내 코드를 호출하면 프레임워크다. JUnit이 `@Test` 메서드를 호출하고 스프링이 객체의 생명주기를 관리하는 것이 대표적인 예다.

## DI: 실행 시점에 의존관계를 주입한다

DI는 IoC를 구현하는 방법 중 하나다. 클라이언트가 사용할 구현 객체를 외부에서 전달하며, 일반적으로 생성자를 통해 주입한다.

DI를 이해하려면 의존관계를 정적 의존관계와 동적 의존관계로 나눠 볼 필요가 있다.

| 구분 | 결정 시점 | 확인 방법 |
| --- | --- | --- |
| 정적 의존관계 | 애플리케이션 실행 전 | 코드를 분석해 확인한다 |
| 동적 의존관계 | 애플리케이션 실행 시점 | 생성된 객체의 연결 관계로 확인한다 |

`Client`의 코드를 보면 `Repo` 인터페이스에 의존한다는 사실을 알 수 있다. 이것이 정적 의존관계다. 하지만 실제로 `MemoryRepo`와 `DbRepo` 중 어떤 객체가 연결되는지는 코드만 보고 확정할 수 없다. 실행 시점에 설정에 따라 결정되는 동적 의존관계이기 때문이다.

```java
// Client의 코드는 그대로 두고 주입할 객체만 바꾼다.
new Client(new MemoryRepo());
new Client(new DbRepo());
```

DI를 사용하면 정적 의존관계를 바꾸지 않고 동적 의존관계만 교체할 수 있다. 반대로 클라이언트가 구현 클래스를 직접 import하거나 `new`로 생성하면 구체 클래스까지 정적으로 의존하게 되어 DIP를 위반한다.

> 객체를 생성하고 관리하면서 의존관계를 연결하는 대상을 IoC 컨테이너 또는 DI 컨테이너라고 한다. 스프링 컨테이너가 이 역할을 담당한다.

## 사용 영역과 구성 영역

결과적으로 애플리케이션은 객체를 쓰는 **사용 영역**과, 객체를 생성하고 연결하는 **구성 영역**으로 나뉜다.

| 구분 | 하는 일 | 담는 코드 | 구현을 바꾸면 |
| --- | --- | --- | --- |
| 사용 영역 | 객체를 쓴다 | 인터페이스에만 의존하는 비즈니스 로직 | 그대로다 |
| 구성 영역 | 객체를 생성하고 연결한다 | 스프링 설정 정보(`@Configuration`, `@Bean`) | 이곳만 바뀐다 |

구현 클래스를 바꿔도 구성 영역(설정 정보)만 바뀌고 사용 영역은 그대로다. 확장에는 열려 있고 변경에는 닫혀 있는, OCP가 지켜지는 구조다.

---

인터페이스만으로는 구현에서 완전히 벗어날 수 없었다. 객체를 만드는 일까지 클라이언트가 떠안고 있었기 때문이다. 그 일을 스프링 컨테이너에 맡기면서, 클라이언트는 객체를 쓰는 일에만 집중하게 된다.

구현이 바뀌어도 클라이언트 코드는 그대로 남는다. 스프링 DI는 편리함을 위한 기능이기 전에, DIP(의존관계 역전 원칙)와 OCP(개방 폐쇄 원칙)를 코드로 지키게 해 주는 장치다.
